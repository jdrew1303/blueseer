# Irish Payroll Module — Screen Specification (Expanding §3 of the Roadmap)

**Status:** Planning/specification only — no application code in scope.
**Scope:** Detailed expansion of §3 "Screen-Level Backlog" from [irish-payroll-2026-roadmap.md](irish-payroll-2026-roadmap.md), following the same screen IDs. This document works through the screens **in the order the exemplar's own flow presents them** (Company Setup → Employee Master → Revenue Details → RPN, matching `thesaurus.ie/docs/2026/processing-starters/`), starting with the first vertical slice: Company & Certificate Setup (S-01–S-03) and the full Employee Maintenance record (S-04–S-13).

## Conventions grounded in the existing BlueSeer codebase (read before the individual specs)

These aren't invented from scratch — they're what `com.blueseer.hrm.EmployeeMaint` (the existing employee-record screen) already does, kept consistent so the new `com.blueseer.pay` module doesn't feel like a foreign codebase:

- **Layout manager:** the existing screens are built with NetBeans' GroupLayout ("Free Design"), generated by the Matisse GUI builder, not hand-written MigLayout/GridBagLayout. New screens in this module should follow the same tool-generated GroupLayout convention for consistency and so the same designer tooling works — I call out `GroupLayout` explicitly per screen below rather than recommending MigLayout, since introducing a second layout paradigm into one codebase is a real maintenance cost the roadmap doesn't ask for.
- **Multi-section records use `JTabbedPane`** hosting one `JPanel` per section, exactly like `EmployeeMaint.form`'s `jTabbedPane1`. S-04 below follows this directly.
- **Naming:** existing code prefixes buttons `bt` (`btadd`, `btupdate`, `btdelete`, `btlookup`) and text fields `tb` (`tbkey`). Kept below.
- **Listener style:** the existing codebase wires `ActionListener`/`MouseAdapter` via the NetBeans-generated `EventHandler` pattern (anonymous inner classes calling a named handler method), not Java 8 lambdas. Kept below for designer-tool compatibility.
- **Lookup/combo binding:** existing screens bind `JComboBox` via a small in-house utility set (`BlueSeerUtils.luml`, `.lual`, `.luinput`, `.ludialog`, `.luTable`) rather than raw `DefaultComboBoxModel` wiring. New screens should use the same utilities for department/PRSI-class/pay-method dropdowns rather than reinventing combo-binding.
- **Async I/O:** existing code already uses `javax.swing.SwingWorker` for long-running calls (`EmployeeMaint.java` imports it directly). **Every RPN/PSR/AECS call in this module (S-14, S-15, S-31, C-14's NAERSA calls) must run on a `SwingWorker`**, not the EDT — this is an existing, established pattern, not new guidance.
- **No `Controller` layer exists yet.** Today, `EmployeeMaint.java` calls `hrmData` (a static-method data-access class) directly from its event handlers — there is no interposed interface. **This is exactly the gap roadmap §1's "inject business objects into views" principle exists to close**, so every Controller interface below is genuinely new architecture for this module, not a rename of something that already exists. Its methods are still implemented, initially, by classes that call into a `payData`-style static class analogous to `hrmData` — the interface is what makes that swappable later, not a mandate to rewrite data access on day one.
- **DTOs:** no `*DTO` classes exist anywhere in the codebase today. This module introduces them (per the user's own template example, `employeeController.savePersonalDetails(EmployeeDTO)`) as the payload contract between View and Controller — plain data carriers, no behaviour, one per screen-section rather than one giant `EmployeeDTO` for all thirteen tabs, so Track A (Layouts) can build against a stub without waiting for the whole record shape to stabilise.
- **Field masking is a deliberate upgrade, not a copy of existing convention.** The current codebase validates via plain `JTextField` plus post-hoc helpers (`BlueSeerUtils.checkLength`); it does not use `JFormattedTextField`/`MaskFormatter` anywhere. Given the exemplar's own emphasis on catching PPS-number and bank-detail errors at entry (§"Processing Starters": *"if an incorrect PPS number is entered, the PPS number will be removed and this field will be left blank"*), this module specifies `JFormattedTextField` with `MaskFormatter`/regex `DocumentFilter` masks where the exemplar's own validation rules justify it. This is flagged explicitly per field below, not silently assumed.

## 3.1 Company & Certificate Setup

### S-01 - New Company Wizard

*   **Component Tree (Passive View):**
    *   `NewCompanyWizardDialog` (`javax.swing.JDialog`, modal, non-resizable) — `BorderLayout`
        *   `CENTER`: `stepCardPanel` (`javax.swing.JPanel`, `java.awt.CardLayout`) — one card per wizard step, matching the exemplar's own step sequence exactly (name/address → registration number → pay frequency → password → finish)
            *   Card `"company-details"`: `JPanel` (`GroupLayout`)
                *   `lblCompanyName` (`JLabel`, "Company Name") + `tbCompanyName` (`JTextField`, max 100 chars, required)
                *   `lblAddress` (`JLabel`) + `taAddress` (`JTextArea`, 4 rows, word-wrap, inside `JScrollPane`)
            *   Card `"registration"`: `JPanel` (`GroupLayout`)
                *   `lblRegNumber` (`JLabel`, "Employer Registered Number") + `tbRegNumber` (`JFormattedTextField` with a `DocumentFilter` regex mask `^\d{7}[A-Za-z]{1,2}$`, since the exemplar states the number is "normally 7 digits and 1 or 2 letters" — masked as a soft warning, not a hard block, because "normally" implies exceptions exist)
                *   `lblRegHelp` (`JLabel`, small italic, "Often the same as your VAT number")
            *   Card `"pay-frequency"`: `JPanel` (`GroupLayout`)
                *   `rbWeeklyMonthly` / `rbFortnightlyMonthly` (`JRadioButton`, in a `ButtonGroup` — mutually exclusive, since the exemplar is explicit that Weekly+Fortnightly is never a valid combination: *"You will be able to run a combination of either Fortnightly & Monthly payroll OR Weekly & Monthly payroll but NOT Weekly & Fortnightly"*)
            *   Card `"password"`: `JPanel` (`GroupLayout`)
                *   `lblPassword1` + `pfPassword1` (`JPasswordField`) / `lblPassword2` + `pfPassword2` (`JPasswordField`, confirmation)
                *   `lblPasswordRule` (`JLabel`, small, "Minimum 4 alphanumeric characters")
        *   `SOUTH`: `navButtonPanel` (`JPanel`, `FlowLayout.RIGHT`) — `btBack` (`JButton`), `btNext` (`JButton`), `btFinish` (`JButton`, disabled until the final card, since `Finish` is only meaningful once a password has been entered per the exemplar), `btCancel` (`JButton`)

*   **Event Listeners:**
    *   `btNext` click → validates the current card's fields (via the Controller, not client-side only — see below) and, if valid, advances `CardLayout` to the next card
    *   `btBack` click → `CardLayout` shows the previous card, no validation
    *   `tbRegNumber` focus-lost → soft-validates the mask and shows an inline warning icon (not a blocking dialog) if it doesn't match, consistent with "normally" allowing exceptions
    *   `btFinish` click → calls the Controller to persist the new company and closes the dialog
    *   `btCancel` click / window-close → discards all entered data, closes the dialog, no Controller call

*   **Controller Interface:**
    *   `ICompanySetupController.validateStep(WizardStep step, CompanySetupDTO partial): ValidationResult` — called on every `btNext` click; returns field-level error messages the view renders inline, matching the roadmap's `EmployerRegistrationValidator` (roadmap §3.1 S-01)
    *   `ICompanySetupController.createCompany(CompanySetupDTO data): CompanyId` — called once, on `btFinish`. Expected behaviour: persists the employer record, initializes the `ITaxYearRules` binding for the current tax year against this new company (roadmap §5), and returns the new `CompanyId` so the caller can immediately navigate to S-03 (Digital Certificate) or S-04 (first employee) — the exemplar's own flow treats certificate setup as an immediate next step, not a separate later task.

### S-02 - Additional PAYE Registrations

*   **Component Tree (Passive View):**
    *   `AdditionalRegistrationsPanel` (`JPanel`, `BorderLayout`)
        *   `CENTER`: `jScrollPane1` containing `tblRegistrations` (`JTable`, non-editable cells, backed by a custom `AbstractTableModel` — columns: Registration Number, Description, ROS Sub-Cert Status)

    *   `tblRegistrations` row selection change → enables/disables `btRemoveRegistration`

*   **Controller Interface:**

    *   `ICompanySetupController.addRegistration(CompanyId id, String registrationNumber, String description): PayeRegistrationDTO`
    *   `ICompanySetupController.removeRegistration(CompanyId id, RegistrationId regId): void` — expected behaviour: also invalidates any ROS sub-certificate bound to that registration (S-03), so the two screens must share the same Controller rather than being independently wired.

### S-03 - Digital Certificate Manager

*   **Component Tree (Passive View):**
    *   `DigitalCertificatePanel` (`JPanel`, `BorderLayout`)
        *   `NORTH`: `jTabbedPane1` (`JTabbedPane`) — tabs `"Employer Certificate"`, `"Agent Certificate"`
            *   Each tab is a `JPanel` (`GroupLayout`):
                *   `lblCertFile` (`JLabel`) + `tbCertPath` (`JTextField`, non-editable, shows the chosen file path) + `btBrowse` (`JButton`, opens `JFileChooser` filtered to `*.p12`/`*.pfx`)
                *   `lblCertPassword` (`JLabel`) + `pfCertPassword` (`JPasswordField`)
                *   `lblCertStatus` (`JLabel`, coloured text — green "Valid, expires DD/MM/YYYY" or red "Invalid/Expired", per the exemplar's own error states: "Invalid Certificate Password", "Error 1014 - Invalid ROS Certificate")
                *   `btSaveCertificate` (`JButton`)
        *   `CENTER`: `jScrollPane2` containing `tblSubCerts` (`JTable`, columns: PAYE Registration Number, Sub-Cert Status) — populated from S-02's registration list
        *   `SOUTH`: `btSetupSubCert` (`JButton`, enabled only when a row is selected in `tblSubCerts`)

*   **Event Listeners:**
    *   `btBrowse` click → `JFileChooser` selection → populates `tbCertPath`, does not yet persist
    *   `btSaveCertificate` click → calls the Controller to validate and store the certificate; on failure, `lblCertStatus` is updated with the specific error rather than a generic dialog (the exemplar documents several distinct named error codes — 1008, 1011, 1014, "internal error" — the Controller should surface which one occurred so the label can be specific, not just "certificate invalid")
    *   `tblSubCerts` selection change → enables `btSetupSubCert`
    *   `btSetupSubCert` click → opens a modal identical in shape to the Employer Certificate tab, scoped to that one registration

*   **Controller Interface:**
    *   `ICertificateController.saveCertificate(CertificateScope scope, byte[] p12Bytes, char[] password): CertificateValidationResult` — `CertificateValidationResult` carries a typed error enum (`INVALID_PASSWORD`, `EXPIRED`, `MALFORMED`, `SERVICE_UNAVAILABLE`) matching the exemplar's own distinct error pages, not a boolean — this is what lets `lblCertStatus` show the specific reason
    *   `ICertificateController.getCertificateStatus(CertificateScope scope): CertificateStatusDTO` — called on panel load and after every save, to populate `lblCertStatus` and expiry date
    *   `ICertificateController.saveSubCertificate(RegistrationId regId, byte[] p12Bytes, char[] password): CertificateValidationResult`

## 3.2 Employee Master (Process Icon 1)

### S-04 - Employee Maintenance (shell)

This is the direct architectural descendant of the existing `com.blueseer.hrm.EmployeeMaint` — same shell pattern (`JTabbedPane` inside a bordered `JPanel`, `New`/`Update`/`Delete` button row, Surname lookup), extended with the Irish-payroll-specific tabs (S-06–S-12) alongside the existing Personal Details concept (S-05). **This screen does not duplicate `emp_mstr` — it extends it**, per the roadmap's package design (§0): the Personal Details tab (S-05) writes to the existing `emp_mstr` table via `hrmData`-equivalent calls; the new tabs (S-06 onward) write to new `emp_pay_ie`-family tables via the new `payData` class.

*   **Component Tree (Passive View):**
    *   `EmployeeMaintPanel` (`JPanel`, `GroupLayout`, titled border "Employee Maintenance" — matches the existing `EmployeeMaint.form`'s `jPanelMain` exactly)
        *   `jPanel3`: `lblSurname` (`JLabel`) + `cbSurnameLookup` (`JComboBox<EmployeeSummaryDTO>`, editable with autocomplete, bound via `BlueSeerUtils.luml`, custom renderer showing "Surname, First Name (Works No.)")
        *   `btAdd` / `btUpdate` / `btDelete` (`JButton`, same left-to-right order and naming pattern as the existing `btadd`/`btupdate`/`btdelete`)
        *   `jTabbedPane1` (`JTabbedPane`) — tabs in the **exact order the exemplar presents them**, since that order encodes the required completion sequence (Personal → Revenue is the one hard dependency; the rest are optional and order-independent but kept in the exemplar's own order for muscle-memory consistency): `"Personal Details"` (S-05), `"Revenue Details"` (S-06), `"Additions"` (S-07), `"Deductions"` (S-08), `"Departments"` (S-09, actually a shared lookup maintained from any employee record), `"Mid-Year Cumulatives"` (S-10), `"HR Details"` (S-11), `"CSO Details"` (S-12)

*   **Event Listeners:**
    *   `cbSurnameLookup` item-selected → calls the Controller to load the full record, populates every tab's fields, enables `btUpdate`/`btDelete`, disables `btAdd`
    *   `btAdd` click → clears `cbSurnameLookup` and every tab to defaults, enables entry, disables `btUpdate`/`btDelete` until a save succeeds
    *   `btUpdate` click → delegates to whichever tab is currently active's own save method (each tab's `Update` action, per S-05 below, is really this button — the exemplar has one `Update` action per tab-worth of data, not one giant save)
    *   `btDelete` click → confirmation dialog, then calls the Controller; **only enabled if the employee has no finalised payslips this tax year** (deleting an employee with payroll history would corrupt the audit trail — this is a BlueSeer-side guard, not something the exemplar documents, added because the exemplar's model assumes a fresh start-of-year import wipes this concern away per §5 of the main roadmap, which BlueSeer's single-running-instance model does not get for free)
    *   `jTabbedPane1` `stateChanged` (tab switch) → if the currently-open tab has unsaved changes, prompts to save/discard before switching (matches `EmployeeMaint.form`'s existing `jTabbedPane1StateChanged` handler, which already exists for this reason)

*   **Controller Interface:**
    *   `IEmployeeMaintenanceController.searchEmployees(String query): List<EmployeeSummaryDTO>` — powers `cbSurnameLookup`'s autocomplete
    *   `IEmployeeMaintenanceController.loadEmployeeRecord(EmployeeId id): EmployeeRecordDTO` — a composite DTO whose sub-objects (`PersonalDetailsDTO`, `RevenueDetailsDTO`, etc.) are exactly what each tab below consumes; loaded once when `cbSurnameLookup` selection changes, not re-fetched per tab
    *   `IEmployeeMaintenanceController.canDeleteEmployee(EmployeeId id): boolean` — backs the `btDelete` enablement guard described above
    *   `IEmployeeMaintenanceController.deleteEmployee(EmployeeId id): void`

### S-05 - Personal Details tab

*   **Component Tree (Passive View):**
    *   `PersonalDetailsTab` (`JPanel`, `GroupLayout`, hosted as a `jTabbedPane1` tab)
        *   `tbSurname` (`JTextField`, required, max 60 chars)
        *   `tbFirstName` (`JTextField`, required, max 60 chars)
        *   `taAddress` (`JTextArea`, 3 rows, inside `JScrollPane`) — **conditionally required**: becomes bordered red and required if `tbPpsNumber` is blank or `dcDateOfBirth` is blank, per the exemplar: *"you must input an address if the employee's PPS number is unknown"*
        *   `dcDateOfBirth` (a date-picker component — `JFormattedTextField` with a `DateFormatter` mask `dd/MM/yyyy` is sufficient; a full `JDateChooser` third-party component is not required) — **conditionally required**: same red-border pattern, required if the employee is calculated to be >66 or <16 given the entered date, or if PPS is unknown (a small chicken-and-egg case: the DOB field's own value is what determines "over 66", so the required-ness of DOB itself is only enforced at save time via the Controller, not live — see Event Listeners)
        *   `tbEmail` (`JFormattedTextField`, basic email-shape regex `^[^@\s]+@[^@\s]+\.[^@\s]+$`) + `pfPayslipPassword` (`JPasswordField`, for payslip PDF encryption)
        *   `cbDirector` (`JCheckBox`, "Director")
        *   `cbDepartment` (`JComboBox<DepartmentDTO>`, bound via `BlueSeerUtils.luml` against S-09's department list; includes a `"— Manage Departments —"` item that opens S-09 as a modal, so the user is never blocked mid-entry)
        *   `tbPpsNumber` (`JFormattedTextField`, mask enforcing 7 digits + 1–2 letters, same pattern as S-01/S-02 but this one is a **hard** mask, not soft — the exemplar states an incorrect PPS number is actively stripped by the system: *"if an incorrect PPS number is entered, the PPS number will be removed and this field will be left blank"* — so BlueSeer should reject the keystroke pattern outright here, unlike the softer employer-registration case)
        *   `tbEmploymentId` (`JTextField`, **non-editable**, grey background — auto-populated, per the exemplar: *"this is an auto-populated field"*)
        *   `tbWorksNumber` (`JTextField`, optional — left blank, the Controller auto-numbers on save)
        *   `tbHourlyRate` (`JFormattedTextField`, `NumberFormatter`, 2 decimal places, currency) and `tbFixedPay` (`JFormattedTextField`, same format, label changes to "Weekly Pay"/"Monthly Pay"/"Fortnightly Pay" depending on the company's pay frequency from S-01) — **mutually exclusive in practice per the exemplar's own guidance** (*"if the employee is not paid by the hour, it is not necessary to enter an hourly rate"*), enforced as a soft warning on save (not a hard block, since some hourly employees also have a small fixed allowance)
        *   `rbPayMethod` (three `JRadioButton`s in a `ButtonGroup`: "Cash", "Cheque", "Credit Transfer") controlling visibility of:
            *   `bankDetailsPanel` (`JPanel`, only visible when "Credit Transfer" selected): `tbBank` (`JTextField`), `tbBranch` (`JTextField`), `tbSortCode` (`JFormattedTextField`, mask `##-##-##` per standard Irish/UK sort-code presentation), `tbAccountNumber` (`JFormattedTextField`, mask `########`, 8 digits), `tbCreditUnionRef` (`JTextField`, optional) — **no BIC/IBAN fields at all**, matching the exemplar exactly: *"There is no need to enter the BIC or IBAN for each employee as the software will automatically convert..."*
        *   `btUpdatePersonalDetails` (`JButton`, "Update")

*   **Event Listeners:**
    *   `tbPpsNumber` focus-lost → calls the Controller's PPS modulus-check; on failure, clears the field and shows an inline warning, exactly reproducing the exemplar's stated behaviour rather than merely blocking future keystrokes
    *   `dcDateOfBirth` focus-lost → recomputes age and, combined with `tbPpsNumber`'s current state, toggles the red-required styling on `taAddress`/`dcDateOfBirth` themselves (a self-referential check, resolved by re-evaluating both fields' required-ness together whenever either changes)
    *   `rbPayMethod` selection change → shows/hides `bankDetailsPanel` via `setVisible` + parent `revalidate()`/`repaint()`
    *   `btUpdatePersonalDetails` click → client-side required-field check, then calls the Controller; on success, advances focus to the "Revenue Details" tab automatically **only when this is a brand-new employee** (`btAdd` was clicked on S-04), reproducing the exemplar's explicit instruction: *"THE EMPLOYEE'S PERSONAL DETAILS ARE NOW COMPLETE. SELECT THE 'REVENUE DETAILS' TAB TO CONTINUE"* — for an existing employee being edited, focus stays put, since forcing navigation on every edit of an existing record would be disruptive

*   **Controller Interface:**
    *   `IEmployeeMaintenanceController.validatePpsNumber(String pps): PpsValidationResult` — wraps the roadmap's `PpsNumberValidator` (roadmap §3.2 S-05); called on focus-lost, not only on save, so the field visibly clears immediately per the exemplar
    *   `IEmployeeMaintenanceController.savePersonalDetails(PersonalDetailsDTO data): SaveResult` — expected behaviour: persists to `emp_mstr` (existing table, extended), runs `EmploymentIdentifierGenerator` if this is a new record (roadmap §3.2 S-05) to populate `tbEmploymentId`, runs `SepaAccountConverter` against the entered sort code/account number **at save time, not live**, storing the derived BIC/IBAN alongside but never displaying them (matching the exemplar's explicit no-BIC/IBAN-field design), and returns whether this was a create or update so S-04's auto-advance behaviour can decide correctly

### S-06 - Revenue Details tab

*   **Component Tree (Passive View):**
    *   `RevenueDetailsTab` (`JPanel`, `GroupLayout`)
        *   `lblEmergencyBanner` (`JLabel`, spans the top, bold, amber background via `setOpaque(true)`/`setBackground`) — **read-only, driven entirely by the Controller**, not a form field — shown whenever the employee's current basis is `EMERGENCY`, reproducing the exemplar's own automatic-and-unavoidable framing: *"the employee will automatically be placed on emergency tax until they are updated by an RPN"* — the user cannot dismiss or edit this banner, only resolve it by successfully retrieving an RPN (S-14/S-15)
        *   `dcStartDate` (`JFormattedTextField`, `dd/MM/yyyy` mask, required)
        *   `tbStartWeek` (`JFormattedTextField`, integer 1–53, **auto-derived** from `dcStartDate` against the Payroll Calendar (S-17) but editable, per the exemplar: *"select their start week number"* is listed as a distinct action from entering the date, implying it is shown but adjustable, not locked)
        *   `cbPrsiClass` (`JComboBox<String>`, populated with the PRSI subclass codes from `ITaxYearRules`, e.g. `A1`, `AX`, `AL`, `J9` — see calc-engine spec C-02) + `btPrsiClassHelp` (`JButton`, small "?" icon, opens a `JOptionPane` or side panel summarising class selection — the exemplar explicitly offers this: *"If unsure of the PRSI Class to apply, a help link is provided"*)
        *   `pnlExemptions` (`JPanel`, `FlowLayout` or `GridLayout` of `JCheckBox`es) — one checkbox per exemption/exclusion type the RPN schema supports (e.g. USC exempt, PRSI exempt) — the exact enumerated list is an EDI-schema question, not a UI-design one, so this spec leaves the exact checkbox set to be filled in once the RPN XML schema's exemption codes are confirmed (see Open Questions)
        *   `btUpdateRevenueDetails` (`JButton`, "Update")

*   **Event Listeners:**
    *   Tab-selected (first time only, for a **new** employee) → if this is a first-ever RPN-less employee, shows a one-time modal reproducing the exemplar's own prompt: *"the employee will automatically be placed on emergency tax until they are updated by an RPN"* — a one-time explanatory nudge, not the persistent banner (the banner itself is always live; this modal just draws attention to it the first time)
    *   `dcStartDate` focus-lost → recalculates `tbStartWeek` against the active `PayrollCalendarService` (roadmap §3.4 S-17), overwriting only if the user hasn't manually edited `tbStartWeek` since the last date change (a simple dirty-flag on `tbStartWeek`, so the auto-derivation doesn't fight a manual correction)
    *   `btUpdateRevenueDetails` click → calls the Controller; **manual entry of credits or cut-off points is not possible anywhere on this tab** — there is deliberately no field for them, matching the exemplar's explicit statement that manual entry "is thus no longer possible" — on success, if this is a new employee record, prompts *"Send an RPN request now?"* and, if confirmed, launches S-14 immediately, reproducing the exemplar's own flow: *"On closing out of the new employee record, you will now be prompted to send an RPN request"*

*   **Controller Interface:**
    *   `IEmployeeMaintenanceController.saveRevenueDetails(RevenueDetailsDTO data): SaveResult` — expected behaviour: persists start date/week/PRSI class/exemptions to the new `emp_rpn_ie`-family table; **does not** touch tax credits or cut-off points (those only ever arrive via S-14/S-15's RPN-import path, never via this screen), matching `EmergencyTaxPolicy` (roadmap §3.2 S-06) auto-applying until an RPN lands
    *   `IEmployeeMaintenanceController.getCurrentEmergencyStatus(EmployeeId id): EmergencyStatusDTO` — polled on tab load and after any RPN import elsewhere in the app affects this employee, to drive `lblEmergencyBanner`

### S-07 - Additions tab

*   **Component Tree (Passive View):**
    *   `AdditionsTab` (`JPanel`, `BorderLayout`)
        *   `NORTH`: `lblOnceOffReminder` (`JLabel`, small italic) — static text reproducing the exemplar's own warning verbatim: *"If this is a once off addition, remember to revert the amount entered to zero in the next pay period"* — kept as a persistent on-screen reminder rather than a one-time dialog, since the exemplar frames this as an ongoing risk, not a one-time gotcha
        *   `CENTER`: `jScrollPane1` containing `tblAdditions` (`JTable`, editable cells, custom `AbstractTableModel`) — columns: Description (`JTextField` cell editor with autocomplete against prior descriptions, per C-19's classification pattern), Taxable? (`JCheckBox` cell editor/renderer — matches the exemplar's binary Taxable/Non-Taxable split exactly, no third option), Amount (custom numeric cell editor, `JFormattedTextField`-backed), End Date (nullable, opens the S-07a modal on click rather than inline editing, since an end date is a distinct sub-workflow per the exemplar)
        *   `SOUTH`: `btAddRow` (`JButton`, "+"), `btRemoveRow` (`JButton`, "−", enabled only with a row selected), `btUpdateAdditions` (`JButton`, "Update")

*   **Event Listeners:**
    *   `btAddRow` click → appends a blank row to the table model, starts cell-editing on the new row's Description cell immediately
    *   `btRemoveRow` click → confirmation only if the row has a non-zero Amount (empty/zero rows are removed silently — they're almost certainly accidental blank rows, not data the user would mourn losing)
    *   Table cell `Description` autocomplete selection from a prior description → auto-fills the Taxable checkbox to match that description's last-used value (a convenience, not a rule — the exemplar itself doesn't specify this, it's a reasonable UX inference from "before proceeding you must first determine if the addition you wish to set up for an employee is 'taxable' or 'non taxable'" being a genuinely easy step to get wrong)
    *   End Date cell click → opens S-07a as a modal, pre-populated with this row's addition
    *   `btUpdateAdditions` click → calls the Controller with the full table contents

*   **Controller Interface:**
    *   `IEmployeeMaintenanceController.saveAdditions(EmployeeId id, List<AdditionLineDTO> lines): SaveResult` — feeds `AdditionCalculationEngine` (roadmap §3.2 S-07); expected behaviour: replaces the full addition set for this employee (the table is the source of truth each save, not a diff/patch), since the exemplar's own model treats this as "what's currently configured," not an append-only log
    *   `IEmployeeMaintenanceController.suggestDescriptions(String partial): List<String>` — powers the Description column's autocomplete, scoped per-employer (not global across all BlueSeer customers)

### S-30 - Week 53 Handling

*   **Component Tree (Passive View):** not a standalone screen — `Week53Banner` (`JPanel`, `FlowLayout`), embedded conditionally at the top of S-18, S-19, and S-22 — `lblWeek53Notice` (explains **Week 1 (non-cumulative) basis** applies this period, not "non-cumulative treatment" vaguely — see below) + `btLearnMore` (opens a small explanatory `JDialog`)

*   **Now backed by a fully-specified engine (C-21), which turned out to be simpler in the part this screen cares about than the original roadmap implied.** C-21's research corrected a real misunderstanding: Revenue's own guidance (TDM Part 42-04-07, Regulation 15 of S.I. No. 345 of 2018) requires the employer to run the Week 53 payment on a **plain Week 1 basis using the latest RPN** — no bespoke extra-credit calculation happens at the point of payment. The credit/rate-band *increase* the original roadmap's business-object name implied is real, but it's a **Revenue-side end-of-year review** (s.480B TCA 1997), not something the payroll run itself computes. This screen's banner should say exactly that — "This payment will be taxed on a Week 1 basis; no additional credits are applied this period" — rather than the vaguer "non-cumulative treatment applies" wording an earlier draft used.

*   **Event Listeners:**
    *   Host panel (S-18/S-19/S-22) load → checks `isWeek53Period` via the Controller and shows/hides the banner accordingly; no other user interaction required beyond the optional `btLearnMore`
    *   `btLearnMore` click → the explanatory dialog should now correctly distinguish the in-period effect (Week 1 basis, applied automatically, nothing for the user to do) from the year-end effect (a Revenue review the *employee's own accountant* handles when filing an Income Tax return, not something this payroll run performs) — conflating the two in the copy would misrepresent what BlueSeer just did

*   **Controller Interface:**
    *   `IPayrollCalendarController.isWeek53Period(CompanyId id, int periodNumber): boolean` — backs `Week53DetectionService`
    *   `IPayEntryController`'s existing pay-calculation methods (S-18/S-19's `savePayEntry`/`saveQuickEditBatch`) now pass C-21's `effectiveCalculationBasisForPeriod` output into the same `IPayrollCalculationService` facade every other payslip line uses — **no new Controller method is needed on this screen at all**, since forcing Week 1 basis is a parameter to the existing calculation call, not a separate calculation path. This is a direct consequence of C-21's finding that the in-period mechanism reuses C-01's already-specified Week1 basis rather than requiring new math.
    *   A **separate, optional** informational screen (not yet in the roadmap's §3 backlog — worth adding on request) could expose C-21's end-of-year credit/band-increase preview to accountants preparing the employee's Income Tax return via the Year End Summary (S-46), but that is explicitly **not** part of S-30/S-18/S-19/S-22's real-time payroll flow

## Open Questions for This Expansion

Carried forward from the first vertical slice:

1. **S-06's exemption/exclusion checkbox set** (`pnlExemptions`) is left as "however many the RPN schema defines" rather than an enumerated list — needs the actual RPN XML schema (from `com.blueseer.edi`'s eventual ROS integration work) before the exact checkboxes can be named.
2. **S-12's CSO occupation-code and hours-category reference lists** need to be sourced from the CSO's own EHECS classification publication (not yet fetched in this session) before `cbOccupationCode`'s actual options can be hardcoded/seeded.
3. **S-04's `canDeleteEmployee` guard** (no deletion once payslips exist this tax year) is a BlueSeer-side design decision, not something the exemplar documents — worth explicit product sign-off.
4. **Field masking is specified more strictly than the existing codebase's convention** — confirm the team is fine introducing `JFormattedTextField`/`DocumentFilter` masking as this module's local convention before Track A starts building.

Gaps closed in a follow-up research pass (kept here, marked resolved, so the history of what was wrong and what fixed it isn't lost):

5. ~~`IllnessBenefitReconciliationService` (S-57) had no corresponding calc-engine spec entry~~ — **resolved.** C-22 confirms Illness Benefit is structurally identical to C-18 (RPN credit-reduction, USC/PRSI-exempt, never added to gross pay); the one new piece — the DSP-to-employer mandate reimbursement — turned out to be entirely outside payroll (a bookkeeping receipt, not a payslip line), which is itself the useful finding. S-57 above now reflects this directly.
6. ~~`Week53TaxTreatment` (S-30) had the same gap~~ — **resolved, and the original framing was backwards.** C-21 (TDM Part 42-04-07, Regulation 15 of S.I. No. 345 of 2018, fetched directly) shows the in-period payroll effect is just "force Week 1 basis" — reusing C-01's existing mechanics, no new formula — while the credit/rate-band *increase* the roadmap's naming implied is a Revenue-side end-of-year review (s.480B TCA 1997), not a payroll-time calculation at all. S-30 above has been rewritten to match.
7. **CWPS and NECI pension rate tables (S-59) — CWPS resolved, NECI still lower-confidence.** C-23 (CWPS) is fully sourced from the scheme administrator's own published rate card — a flat weekly-euro structure, not percentage-of-earnings, which changed S-59's UI shape for that card entirely (no rate-entry fields at all, since nothing is user-configurable). C-24 (NECI) is built from two consistent secondary sources only; no primary NECI or Revenue document was located. S-59's NECI card now surfaces that uncertainty directly to the user (an on-screen warning label) rather than silently presenting an unverified figure as fact — do not remove that warning until C-24 gets a primary-source pass.
8. **S-06's PRSI-class help content** (`btPrsiClassHelp`) needs actual copy summarizing class selection — this document specifies that the button exists and what it should broadly contain, not the copy itself, since that's a content-writing task rather than an architecture question.
9. **Reused components appear in multiple sections** (`CheckRevenueRecordPanel` in S-35/S-70; the report-picker shape across all of §3.8; `PostCessationPaymentPanel` in S-51/S-52; `ImportHoursWizard` in S-28/S-29) — Track A should build these once as shared components from the start, not as five separate near-identical panels later merged in a refactor. This is called out explicitly per-screen above, not left implicit.
10. **Every screen's field-level `Controller` method assumes the roadmap §4.1 interfaces are frozen first** — this document, like the roadmap itself, treats that freeze as the first ticket blocking Track A/B/C/D. Nothing here should be built against before that happens.
